# kr-service-style — 국내 서비스식으로 다듬기

국내 서비스가 **공식으로 공개한** 원칙·문구 규칙·화면 패턴으로 기존 화면을 다듬는다. 겉모양(색·로고·서체)을 베끼지 않고, 그 서비스가 화면을 그렇게 만드는 **이유**를 가져온다.

## 0. 서비스와 범위 고르기

인자로 받을 수 있다: `/gv-workflow:kr-service-style <서비스> [범위]` — 예: `toss`, `toss 문구`, `karrot ux,ui`

**서비스나 범위가 인자·말에 없으면 시작하기 전에 AskUserQuestion 한 번으로 둘 다 묻는다.** 추측해서 시작하지 않는다. "토스처럼" 처럼 서비스만 말했으면 범위만 묻는다.

1. **서비스** (하나 고르기)
   - 토스 — 한 화면 한 행동, 해요체, 공개 자료가 가장 많음 → `profiles/toss.md`
   - 당근 — SEED 디자인 시스템 토큰(간격·모서리·글자), 문구 규칙 → `profiles/karrot.md`
   - 네이버·카카오·배민 — 공개 원칙이 거의 없어 서체·로그인 버튼·상표 경계 위주 → `profiles/brands.md`
2. **범위** (여러 개 고르기, 기본은 셋 다)

| 범위             | 보는 것                                             | 기존 시안에서 바뀌는 것                  | 건드리지 않는 것  |
| ---------------- | --------------------------------------------------- | ---------------------------------------- | ----------------- |
| `ux` 사용 흐름   | 화면당 행동 수, 입력 순서, 경고·인증 시점, 다크패턴 | 버튼 위계, 단계 나누기, 요소 빼기·옮기기 | 색·글자 크기·문구 |
| `ui` 화면 모양   | 글자 단계, 색 구조, 간격·모서리, 리스트·그래픽      | CSS 토큰·스타일 값                       | 구조·순서·문구    |
| `문구` UX 라이팅 | 말투, 문장 규칙, 버튼 이름                          | 화면 글자                                | 레이아웃·스타일   |

- **철학**은 범위가 아니다. 각 프로필 맨 위의 철학은 규칙이 애매하거나 부딪힐 때 판단 기준으로만 쓴다
- 고른 프로필 파일을 **전부 읽고**, 고른 범위의 표만 적용한다. 프로필에 없거나 "미확인" 인 규칙을 "그 회사라면 이럴 것" 으로 지어내지 않는다
- 네이버·카카오·배민: `brands.md` 에서 고른 범위 태그가 붙은 항목만 쓰고, 그 범위에서 비는 부분은 `toss.md` 의 같은 범위로 채운다. 그렇게 했다고 결과 맨 위에 적는다
- 로그인 버튼(카카오·네이버)이 화면에 있으면 서비스·범위와 상관없이 `brands.md` 의 버튼 가이드로 점검한다
- 특정 서비스 없이 "국내 앱 느낌" 이라고만 하면 질문의 서비스 첫 번째에 "(추천)" 을 붙여 토스를 권한다

## 1. 재기 (고치기 전)

1. 대상 화면을 연다 (dev 서버 주소나 HTML 파일). 없으면 주소 하나만 묻는다
2. 폭 2개에서 잰다: **390 (모바일), 1440 (데스크톱)**. 모바일 전용 화면이면 390 만
3. 폭마다 페이지 안에서 실행한다 (브라우저 자동화 도구의 JS 실행, 또는 Playwright `page.evaluate`):
   - `window.KR_STYLE_PROFILE = '<프로필>'; window.KR_STYLE_SCOPE = ['ux','ui','writing']` 을 먼저 실행 (고른 범위만, `문구` 는 `'writing'`)
   - 이 스킬 폴더의 `stylecheck.js` 내용을 실행 → 문구·버튼·주 버튼 개수·탭·글자 크기·남의 브랜드 색
   - `gv-workflow:hangul-wrap` 스킬이 있으면 그 `wrapcheck.js` 도 → 어절 쪼개짐
4. 화면 캡처를 한 장 남긴다 (전·후 비교용)
5. 브라우저를 쓸 수 없으면 소스 코드만 읽고 진행하되, 결과 맨 위에 **"실측 안 함"** 이라고 적는다

## 2. 고치기

고른 범위를 **ux → ui → 문구** 순서로 본다 (구조가 바뀌면 스타일·문구도 따라 바뀌니까). 프로필 표의 "찾을 것" 으로 시안을 훑고, "바꾸는 법" 대로 고친다. 검사기가 잡은 것은 후보다. 맥락을 보고 고칠지 판단한다 (예: 정말 작업을 취소하는 버튼이면 "취소" 가 맞다).

**ux**

- 버튼 위계 바꾸기, 요소 빼기·접기는 바로 고친다
- 화면을 여러 단계로 나누거나 순서를 바꾸는 것은 **바꿀 구조를 표로 먼저 보여 주고 확인받은 뒤** 고친다 (라우팅·상태가 바뀌는 큰 수정)

**ui**

- 크기·간격·둥글기: 프로필에 공식 값이 있으면 그 값을, "미확인" 이면 프로젝트의 기존 토큰을 쓴다
- 색: **사용자 브랜드 색**을 프로필의 색 구조(진한 채움 / 연한 바탕 / 회색 단계)에 끼운다. 브랜드 색이 없으면 하나만 묻는다
- 서체: 전용 서체는 쓰지 않는다. 프로젝트 서체를 유지하거나 OFL 서체(Pretendard, 나눔, 카카오 글씨 등)를 제안하고, 라이선스 고지를 함께 넣는다

**문구**

- 뜻을 바꾸지 않는다. 금액·날짜·조건·법적 고지는 그대로 두고 말투만 바꾼다
- 고친 문구는 전·후를 표로 남긴다

**하지 않는 것**

- 회사 로고·심볼·캐릭터·아이콘·그래픽을 넣는 것
- 브랜드 색(토스 파랑, 카카오 노랑, 네이버 그린, 당근 주황)을 주색으로 쓰는 것
- 사용자 서비스를 그 회사 서비스로 오인하게 하는 문구 ("토스 공식", "for Kakao" 등)
- 고치라고 한 화면 밖까지 손대는 것 — 같은 문제가 보이면 목록으로 알리고 묻는다

## 3. 다시 재기

1단계와 같은 폭·같은 프로필·같은 범위로 다시 실행하고 캡처한다. 보고:

```markdown
**서비스** toss · **범위** ux, 문구 · **실측** 390, 1440 (Playwright)

| 범위 | 규칙            | 전  | 후  | 남은 이유                  |
| ---- | --------------- | --- | --- | -------------------------- |
| ux   | 주 버튼 여러 개 | 3   | 0   |                            |
| 문구 | 합니다체        | 5   | 1   | 약관 고지 문구 — 원문 유지 |

| 문구 전                | 문구 후    | 근거                            |
| ---------------------- | ---------- | ------------------------------- |
| 송금이 완료되었습니다. | 송금했어요 | toss.md 문장 규칙 (능동·해요체) |
```

- 검사기가 못 보는 규칙(입력 순서, 경고 시점 등)은 "눈으로 확인" 으로 따로 적는다
- 0이 아닌 항목은 남긴 이유를 적는다
- 돌리지 못한 검사는 통과로 적지 않는다

## 검사기 한계

- 문구 규칙은 정규식 근사다. 존댓말이 필요한 맥락(고객센터 공지, 법적 고지)은 사람이 판단한다
- 주 버튼은 "채도 있는 배경의 버튼" 으로 추정한다. 브랜드 색이 회색 계열이면 못 잡는다
- 남의 브랜드 색은 RGB 거리로 비교한다. 비슷하지만 다른 색(거리 24 이상)은 통과한다
- 배민 민트는 공식 값을 찾지 못해 검사하지 않는다

## 다른 도구

- 이 스킬은 기존 화면을 공식 출처 기준으로 다듬고 재는 데 집중한다
