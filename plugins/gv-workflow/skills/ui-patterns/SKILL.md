# ui-patterns — 디자인 요소 알려 주고, 어울리는 걸 골라 적용하기

이름이 다른 요소는 **동작 약속**이 다르다. 토글은 "누르면 바로 반영", 스낵바는 "누를 시간을 준다", 모달은 "답할 때까지 멈춘다".
요소의 이름·고르는 기준·만드는 법·흔한 실수는 `patterns.md` 에 묶음별로 있다. **맨 위 목차를 보고 해당 묶음만 읽는다.**

## 0. 할 일 정하기

| 말                                                    | 할 일       | 단계                |
| ----------------------------------------------------- | ----------- | ------------------- |
| "로딩 종류 알려줘", "모달 말고 뭐 있어"               | 알려 주기   | 1                   |
| "여기 뭐 쓰면 좋아", "어울리는 걸로", "토스트 만들어" | 고르고 적용 | 2 → 3 → 4           |
| "컴포넌트 봐줘", "이 화면 이상해"                     | 고치기      | 4(재기) → 2 → 3 → 4 |

애매하면 AskUserQuestion 한 번으로 묻는다.

## 1. 알려 주기

- 해당 묶음의 표를 그대로 보여 주지 말고 **사용자 화면·상황에 걸리는 것부터** 3–5개를 고른다. 각각 이름 · 한 줄 차이 · 언제
- 사용자 프로젝트가 있으면 "이 저장소에서는 `components/Toast.tsx` 가 사실 스낵바예요" 처럼 실제 자리를 짚는다
- 끝에 "적용할까요?" 대신 다음에 할 수 있는 것 하나를 권한다 (예: "주문 완료에 완료 화면 넣기")

## 2. 고르기 — 어울리는 것을 추천하고 사용자가 고른다

1. **상황을 읽는다**: 화면·코드를 보고 4가지를 적는다 — 기기(모바일/데스크톱), 일의 크기·되돌릴 수 있는지, 얼마나 멈춰 세워도 되는지, 이미 쓰는 요소·라이브러리
2. 묶음 표의 "고르는 기준" 에 대 보고 후보 2–4개를 추린다
3. **AskUserQuestion 한 번**으로 고르게 한다
   - 맞는 것을 첫 번째에 놓고 라벨 끝에 "(추천)", 설명에 **그 화면에서 왜**를 한 줄
   - 생김이 다른 후보(모달 vs 바텀시트, 디자인 스타일)는 `preview` 에 ASCII 시안을 넣는다
   - 한 화면에 여러 자리가 있으면 질문을 자리별로 (최대 4개)
4. 사용자가 이름을 콕 집었는데 상황과 안 맞으면(저장 버튼 있는 설정 화면에 "토글") 그것을 막지 않되, 맞는 쪽을 "(추천)" 으로 함께 내놓는다
5. 디자인 스타일(12번)은 한 화면에 하나. 시안이 필요하면 고르기 전에 후보 2개를 실제 페이지로 띄워 보여 준다

## 3. 적용하기

- **네이티브 먼저**: `<dialog>`, `popover`, `<progress>`, `<meter>`, `role="switch"`, `role="status"`, `navigator.share`. 이걸로 되면 라이브러리를 새로 들이지 않는다. 프로젝트에 이미 쓰는 컴포넌트 라이브러리(Radix, shadcn 등)가 있으면 그걸 쓴다
- 색·간격·둥글기는 프로젝트 토큰. 브랜드 색은 바꾸지 않는다
- 움직임은 짧게(작은 피드백 0.2–0.4초, 큰 것 1초 안팎), `prefers-reduced-motion: reduce` 에서 끈다
- 요소를 **바꾸는** 수정(모달 → 바텀시트, 토글 → 체크박스+저장, 무한 스크롤 → 더보기)은 상태·라우팅이 바뀔 수 있으니 바꿀 목록을 표로 보여 주고 확인받은 뒤 고친다. 이름·aria·safe-area 같은 작은 수정은 바로 고친다
- 선택 심리(13번)는 숫자·재고·후기가 실제 데이터일 때만. "선을 넘으면" 칸에 걸리는 요청은 하지 않고 이유를 말한다
- 고치라고 한 화면 밖에서 같은 문제를 보면 목록으로 알리고 묻는다

## 4. 재기 (적용 전·후)

1. 대상 화면을 연다. 없으면 주소 하나만 묻는다. localhost 는 저장소의 Playwright 로
2. 폭 2개: **390, 1440**. 모바일 전용이면 390 만
3. 폭마다 이 스킬 폴더의 `uicheck.js` 내용을 페이지 안에서 실행한다 (Playwright `page.evaluate(코드)` 또는 브라우저 자동화 도구의 JS 실행)
4. **창·토스트·시트·메뉴는 열어 둔 상태에서 한 번 더** 실행한다 (닫혀 있으면 못 잡는다)
5. 캡처를 남기고, 바뀐 화면은 브라우저로 띄워 사용자에게 보여 준다
6. 브라우저를 못 쓰면 소스만 읽되 결과 맨 위에 **"실측 안 함"**

눈으로 볼 것(검사기 밖): 토스트가 떠 있는 시간, 스낵바 호버 멈춤, 스와이프·드래그의 대체 버튼, 모달 Esc·포커스 복귀, 완료 피드백 크기, 스타일 적용 뒤 글자 대비.

보고:

```markdown
**실측** 390, 1440 (Playwright) · 열어서 잰 것: 필터 시트, 저장 토스트

| 자리      | 전               | 고른 것 (후보)                  | 근거           |
| --------- | ---------------- | ------------------------------- | -------------- |
| 알림 설정 | 토글 + 저장 버튼 | 토글, 즉시 저장 (체크박스+저장) | patterns.md 1  |
| 주문 완료 | 토스트           | 완료 화면 (토스트, 컨페티)      | patterns.md 11 |

| 묶음        | 규칙           | 전  | 후  | 남은 이유                        |
| ----------- | -------------- | --- | --- | -------------------------------- |
| 고르기·입력 | 토글+저장 버튼 | 3   | 0   |                                  |
| 알림·피드백 | 토스트에 버튼  | 1   | 1   | 스낵바로 바꿈 — 클래스 이름 남음 |
```

- 0이 아닌 항목은 남긴 이유를 적는다
- 돌리지 못한 검사, 열어 보지 못한 창은 통과로 적지 않는다

## 검사기 한계

- 클래스 이름(toast·modal·switch·strength 등)으로 요소를 추정한다. 이름이 전혀 다르면 못 잡는다
- 시간(토스트가 몇 초 떠 있는지)·몸짓·대비·심리 패턴은 재지 않는다
- 동작이 있어야 보이는 것도 재지 않는다: 치는 도중 오류(16번), 제출 뒤 오류 요약 포커스(16번), 열자마자 뜨는 권한 요청(18번). 필요하면 Playwright 로 입력·제출을 해 보고 눈으로 확인한다
- `작은 누르는 칸` 은 WCAG 2.5.8 예외를 근사한다 — 글자 링크는 빼고, 작아도 중심 24px 안에 다른 누를 곳이 없으면 통과
- 다른 출처 CSS 는 읽지 못해 `움직임 줄이기 없음`·`아래 고정 safe-area 없음` 을 잘못 낼 수 있다
