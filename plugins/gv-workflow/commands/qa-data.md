# /qa-data — 데이터 전문가 집단 QA 감사

데이터 QA, JSON 스키마, 데이터 정합성, 커버리지, 점수·평가 로직 감사

데이터 파일 스키마·평가 로직 무결성·데이터 커버리지·데이터 정합성을 검사하는 4개 서브에이전트(A1~A4)를 병렬 실행하고 통합 리포트와 점수를 냅니다. **감사·보고만 합니다.** 사용자가 따로 요청하기 전에는 코드나 데이터를 수정하지 않습니다.

대상: 저장소 안에 **구조화된 데이터 파일**(JSON/CSV/YAML/NDJSON 등)이나 **스키마 정의**, **점수·가중치·등급을 계산하는 평가 로직**이 있는 프로젝트. 이런 것이 없으면 해당 에이전트는 "해당 없음"으로 끝난다.

## Usage

`/gv-workflow:qa-data` — 저장소 전체 감사
`/gv-workflow:qa-data public/data` — 지정한 경로(파일·디렉토리)만 감사

인자(`$ARGUMENTS`)가 있으면 그 경로를 감사 범위로, 없으면 저장소 루트 전체를 범위로 잡는다. 지정한 경로가 없으면 바로 멈추고 알린다.

## Action

### 1. 탐색 (메인 에이전트가 직접, 수정 없이)

서브에이전트는 이 대화를 볼 수 없으므로, 아래 결과를 **구체적인 경로로** 정리해 모든 프롬프트에 그대로 넣는다. 항상 제외: `node_modules`, `.git`, `dist`, `build`, `.next`, `coverage`, `vendor`, `.venv`, 락파일, 도구 설정 파일(`package.json`, `tsconfig*.json`, `.eslintrc*`, `*.config.*` 등), 테스트 fixture(별도 표시).

| 항목 | 찾는 방법 |
|------|----------|
| 스택 | `package.json` / `pyproject.toml` / `requirements.txt` / `go.mod` 등 |
| 데이터 파일 위치 | `*.json`, `*.csv`, `*.tsv`, `*.yaml`, `*.ndjson` 을 위 제외 후 검색 → 디렉토리별 파일 수로 요약 |
| 데이터 그룹 구조 | 같은 파일명이 여러 디렉토리에 반복되는 패턴(예: `<엔티티>/<카테고리>.json`) → 엔티티 차원·카테고리 차원 추정 |
| master/detail 관계 | 목록 파일(id/ticker/slug 배열)과 개별 상세 파일이 나뉘어 있는지 |
| 스키마 정의 | `*.schema.json`, Zod/Yup/Joi, Pydantic, TypeScript 타입/인터페이스, DB 마이그레이션 |
| 평가 로직 | `score`, `weight`, `evaluat`, `rating`, `grade`, `rank` 를 Grep → 점수·가중치 계산 파일 목록 |
| 데이터 소비처 | 데이터 파일을 import/fetch 하는 코드 위치 |
| 오늘 날짜 | 신선도 판단 기준 |

탐색 결과 데이터 파일·스키마·평가 로직이 **모두 없으면** 서브에이전트를 띄우지 말고 "해당 없음 — 구조화 데이터와 평가 로직을 찾지 못함"과 근거(확인한 패턴)만 보고하고 끝낸다. 일부만 있으면 4개 모두 띄우고, 대상이 없는 에이전트는 스스로 "해당 없음"을 보고한다.

### 2. 서브에이전트 4개 병렬 실행

**4개를 한 메시지에서 동시에** Agent(Task) 도구 `general-purpose` 로 띄운다. 각 프롬프트 = 아래 **공통 머리말** + 해당 에이전트 블록.

#### 공통 머리말 (모든 프롬프트 맨 앞에 채워서 넣기)

```
프로젝트 루트: <절대 경로>
감사 범위: <$ARGUMENTS 또는 "저장소 전체">
제외 경로: <탐색에서 정한 목록>
오늘 날짜: <YYYY-MM-DD>
탐색 결과:
- 스택: <...>
- 데이터 파일 위치: <디렉토리: 파일 수, ... | 없음>
- 데이터 그룹 구조: <예: data/<entity>/<category>.json, 엔티티 N개 | 없음>
- master/detail: <목록 파일 → 상세 파일 경로 패턴 | 없음>
- 스키마 정의: <경로 | 없음>
- 평가 로직: <파일 목록 | 없음>
- 데이터 소비처: <파일 목록>

## 규칙
- 읽기 전용: 파일을 절대 수정·생성하지 마세요. 감사 결과만 보고합니다.
- 모든 발견 항목에 근거를 붙이세요: 코드는 `파일:라인`, 데이터는 `파일:라인` 또는 `파일 → JSON 경로`(예: `data/a.json → $.items[3].date`). 근거를 댈 수 없으면 그 항목은 빼세요.
- 체크 항목의 대상이 프로젝트에 없으면 "해당 없음 — <이유>"로 쓰세요. 없는 문제를 만들지 마세요.
- 큰 파일은 전체를 읽지 말고 `jq`, `head`, 스크립트(읽기 전용)로 구조·통계를 뽑으세요.
- 같은 패턴이 많으면 대표 3~5건 + 총 건수로 묶으세요.

## 심각도
- CRITICAL: 잘못된 값이 사용자에게 표시되거나 렌더링·계산이 깨지는 문제
- HIGH: 파싱 오류 가능, 가짜·더미 데이터, 커버리지 큰 격차
- MEDIUM: 개선 권장

## 출력 형식
## <에이전트명> 감사 결과
### <체크 항목명>
- CRITICAL|HIGH|MEDIUM: [근거] 설명
(해당 없음이면 "해당 없음 — 이유")
### 요약
총 N건 (Critical: X, High: Y, Medium: Z) / 해당 없음 항목: [...]
```

#### A1-Schema (데이터 스키마 검증)

```
## 역할: 데이터 스키마 검증 전문가 (A1-Schema)

### 1. 같은 종류 파일 간 필드 구조 비교
- 데이터 그룹 구조에서 같은 카테고리(같은 파일명/같은 역할)인 파일들을 엔티티 간 비교.
- 필드명 불일치(camelCase vs snake_case 포함), 누락 필드, 추가 필드.
- 스키마 정의가 있으면 데이터가 스키마를 따르는지(필수 필드, 타입, enum) 확인.

### 2. 빈 데이터 파일
- `[]`, `{}` 만 있는 파일, 10바이트 미만 파일, 헤더만 있는 CSV.

### 3. 타입 일관성
- 같은 필드가 파일/레코드마다 다른 타입(숫자 vs 문자열 등).
- `null` 비율이 50% 이상인 필드.
- 날짜 필드(`date`, `dt`, `timestamp`, `*_at` 등) 형식 불일치.

### 4. master/detail 참조 일치
- 목록 파일의 id/ticker/slug 와 상세 파일·하위 데이터의 키가 일치하는지. 한쪽에만 있는 키 목록.

심각도 가이드: 같은 카테고리 간 구조 불일치·스키마 위반(소비 코드가 깨짐) = CRITICAL, 빈 파일·타입 불일치·참조 불일치 = HIGH, null 비율·날짜 형식 = MEDIUM
```

#### A2-Eval (평가 로직 무결성)

```
## 역할: 평가·점수 로직 무결성 감사 전문가 (A2-Eval)
평가 로직이 "없음"이면 전체를 "해당 없음"으로 보고하세요.

### 1. 중복 평가 시스템
- 같은 대상을 평가하는 구현이 둘 이상인지(예: JS 버전과 TS 버전, 구버전과 신버전).
- 각 구현의 가중치·카테고리·임계값을 표로 비교.
- import/호출을 추적해 실제로 쓰이는 쪽과 죽은 쪽을 구분. 둘 다 쓰이면서 결과가 다르면 CRITICAL.

### 2. 가짜 점수 생성
- 해시→실수 변환, `Math.random`, 시드 난수, 하드코딩 상수로 실제 데이터가 없는 대상에 점수를 만드는 코드.
- 그 점수가 실제 점수와 구분 없이 UI·출력으로 나가는지 추적. 영향 대상과 점수 범위.

### 3. 출처·근거 데이터
- 평가 근거로 쓰는 소스 URL·출처 목록에 `example.com`, `placeholder`, `TODO` 등 더미 값.
- 그 값이 UI에 렌더링되는 경로.

### 4. 가중치·등급 경계 검증
- 모든 가중치 객체의 합(100 또는 1.0)이 맞는지.
- 등급 경계(예: A ≥ 80)의 빈틈·겹침, 경계값 처리(`>` vs `>=`).
- 0으로 나누기, 결측값을 0점으로 처리해 점수를 왜곡하는 경우.

심각도 가이드: 결과가 다른 중복 평가 시스템·가중치 합 오류 = CRITICAL, 가짜 점수·더미 출처 노출 = HIGH, 경계·결측 처리 = MEDIUM
```

#### A3-Coverage (데이터 커버리지)

```
## 역할: 데이터 커버리지 감사 전문가 (A3-Coverage)
데이터 그룹 구조가 "없음"이면 1·2번은 "해당 없음".

### 1. 엔티티별 파일 수 비교
- 탐색 결과의 엔티티 차원(디렉토리 등)마다 파일 수를 세어 표로. 엔티티를 하나도 빠뜨리지 마세요.
- 가장 많은 쪽과 가장 적은 쪽을 표시.

### 2. 카테고리 커버리지
- 모든 엔티티가 같은 카테고리를 갖는지. 일부 엔티티에만 있는/없는 카테고리 목록.

### 3. master/detail 커버리지
- 목록에 있는 항목 수 vs 상세 데이터가 있는 항목 수, 빠진 항목 목록.

### 4. 데이터 신선도
- 엔티티별 가장 최근 날짜(데이터 안의 날짜 필드 기준, 없으면 "판단 불가").
- 오늘 기준 30일 이상 지난 데이터.

출력에 엔티티별 비교 표를 포함:
| 엔티티 | <카테고리/디렉토리 A> 파일 수 | <B> 파일 수 | 총계 |

심각도 가이드: 핵심 카테고리 완전 누락 = CRITICAL, 2배 이상 불균형·master/detail 불일치 = HIGH, 신선도·마이너 카테고리 = MEDIUM
```

#### A4-Integrity (데이터 정합성)

```
## 역할: 데이터 정합성 감사 전문가 (A4-Integrity)

### 1. Mock/더미 URL·값
- 데이터 파일과 소스 코드에서 `example.com`, `placeholder`, `dummy`, `lorem`, `foo/bar`, `test` 성 URL·값 검색 (테스트 디렉토리·fixture 제외).

### 2. 날짜 형식
- ISO 8601 과 커스텀 형식(`2024-01-01`, `01/01/2024`, epoch 초/밀리초) 혼용.
- 파싱 불가능한 날짜, 미래 날짜, 명백히 잘못된 연도.

### 3. 금액·숫자 형식
- 숫자여야 할 값이 `"$1,234"` 같은 문자열.
- 퍼센트가 0~1 과 0~100 범위로 혼용.
- 음수가 될 수 없는 필드(가격, 수량, 시가총액 등)의 음수, `NaN`/`Infinity` 문자열.

### 4. 중복·빈 값
- 같은 파일 안의 중복 레코드(같은 키·같은 날짜).
- 빈 문자열 `""` 이 비정상적으로 많은 필드.

### 5. 소스 코드 속 하드코딩 더미 데이터
- 프로덕션 코드에 남은 샘플 배열·고정 응답, `TODO`/`FIXME`/`HACK` 주석과 붙은 하드코딩 값.

심각도 가이드: 더미 값이 UI에 노출될 수 있음·잘못된 값 표시 = CRITICAL, 형식 혼용(파싱 오류 가능)·하드코딩 더미값 = HIGH, 중복·빈 값 = MEDIUM
```

### 3. 검증 및 통합 리포트

서브에이전트 보고를 그대로 믿지 않는다. **모든 CRITICAL 과 HIGH 중 표본**은 메인 에이전트가 근거 위치를 직접 열어 확인하고, 맞지 않으면 빼거나 심각도를 낮춘다. 영역 간 중복(예: A2·A4 의 더미 URL)은 하나로 합친다.

```
# 데이터 QA 감사 리포트

- 범위: <경로 | 저장소 전체>
- 데이터: <파일 수, 위치 요약> / 평가 로직: <파일 수 | 없음>

## 요약
| 영역 | Critical | High | Medium | 총계 |
|------|----------|------|--------|------|
| A1-Schema | X | Y | Z | N |
| A2-Eval | X | Y | Z | N |
| A3-Coverage | X | Y | Z | N |
| A4-Integrity | X | Y | Z | N |
| **합계** | X | Y | Z | N |

해당 없음: <영역/항목 — 이유>

## 점수: NN / 100 — 판정: PASS | 조건부 PASS | FAIL

## Critical 이슈 (즉시 수정 필요)
1. [영역] [근거] 문제 — 수정 방향

## High 이슈
## Medium 이슈
```

**점수** = `100 − (Critical×10 + High×3 + Medium×1)`, 최소 0. 영역 전체가 해당 없음이면 그 영역은 계산에서 빼고 리포트에 명시한다. 4개 영역이 모두 해당 없음이면 점수 대신 "해당 없음".
**판정**: Critical 1건 이상 → FAIL / Critical 0 + High 4건 이상 → 조건부 PASS / 그 외 → PASS.

리포트 뒤에는 "수정할까요? (전체 / Critical만 / 번호 지정)" 한 줄만 묻고 멈춘다.

## 중요 규칙

1. **보고 전용**: 이 커맨드 안에서는 코드·데이터 파일을 수정하지 않는다. 수정은 사용자가 리포트를 보고 요청할 때만.
2. **병렬 실행**: 4개 서브에이전트를 한 메시지에서 동시에 띄운다.
3. **경로 명시**: 서브에이전트 프롬프트에 탐색한 실제 경로·구조를 넣는다.
4. **증거 기반**: 모든 이슈에 `파일:라인` 또는 `파일 → JSON 경로`. 근거 없는 항목은 버린다.
5. **해당 없음 허용**: 구조화 데이터나 평가 로직이 없으면 "해당 없음". 억지로 이슈를 만들지 않는다.
6. **반복 실행 가능**: 수정 후 다시 실행해 해소 여부를 확인한다.
